# An agent writes the library, and its JSON files are the source of truth

Alex decided on 2026-10-09 that no human will want to hand-edit a component definition or a connector type. Library entries are written by an LLM agent through one skill, `harnessy-library`, from whatever the engineer has: a datasheet PDF, a product page, a part number, a photo of the connectors, or a sentence. The skill covers every kind of entry, because a new board brings new connector types with it. A component definition it writes brings any missing connector types along, written to the same place after a check of the merged library. The skill asks the engineer for a pin count or a designator it cannot read from a source. It writes `TBD` only for part numbers. Every entry gains an optional `source` string that names the URL, datasheet or photo it came from.

The repo library used to be generated by `scripts/build-library.ts`, which clears `library/` on every run. That script runs one last time and is retired, so `library/*.json` is what the agent edits in the repo and in a project alike. The skill writes into the opened project's `library/` by default. It writes into the repo library only when the engineer calls the entry common, and promoting a project entry means moving its file into the repo. The skill lives in this repo under `skills/harnessy-library/` and is installed once by symlinking it into `~/.claude/skills`, so it works from any project folder. It validates with a new `pnpm validate <project folder>` run in the Harnessy repo, found through `HARNESSY_REPO`. That command loads both libraries the way the app does and prints every problem.

The connector drawer's type picker ends with a "Not in the library?" line that copies a ready prompt for the agent. The app rereads the project's `library/` when its window regains focus, so a new type appears without reopening the folder. The app never calls an LLM itself. Connector types carry no pin names, and a connector type's 3D body is not this skill's job yet. The decision was made on the ticket [How does an agent author library entries, and which common entries does the repo library carry?](https://github.com/alexchunlin/harnessy/issues/38).

## Considered options

- Keep `build-library.ts` and have the agent edit TypeScript. Rejected: a project's `library/` has no script, so the agent would need two ways to write.
- A skill per kind of entry. Rejected: an engineer rarely asks for one kind alone.
- Publish the skill as a Claude Code plugin with this repo as its marketplace. Rejected: every skill edit would need a version bump.
- Copy the skill into each project folder. Rejected: the copies drift apart.
- Per-field confidence flags on entries. Rejected: a single `source` string tells a later reader where to check, and `TBD` already marks what is unknown.
- An in-app chat that calls an LLM. Rejected: the engineer already runs an agent, and the app stays free of API keys.
