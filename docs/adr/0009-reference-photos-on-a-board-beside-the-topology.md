# Reference photos live in the project and show on a board beside the topology view

Alex decides a harness's branching against photos of the CAD and of the real machine. The topology view no longer shows geometry, so a photo under the canvas would line up with nothing. The photos sit instead on a reference board, a pane that opens beside the topology view from the toolbar with its own divider. Photos are copied into a `reference/` folder in the project, next to `cad/`, and `canvas/reference.json` lists them in order with a relative path and an optional caption each. There is one list per project, not one per topology, because the same photos of one machine inform every topology. Photos come in by drag and drop onto the board or through a file picker on it, as JPEG, PNG or WebP. HEIC is refused with a message that says to export as JPEG, since browsers cannot decode it. The server plugin gains an upload route that writes bytes into `reference/` under an opened folder and a read route that serves a file's bytes, both fenced the way the existing routes are; the JSON listing does not change. The board shows one photo at a time with a thumbnail strip along its bottom edge. The wheel zooms around the cursor, a drag pans, a double click fits the photo to the board, and dragging a thumbnail reorders the strip. One dimness slider covers the whole board and is remembered in the browser beside the divider position, not in the project, because it says nothing about the design. Removing a photo from the board deletes its file too, so `reference/` never holds a photo the app cannot show. The board does not open beside the 3D view in this round, where the reference model is the underlay, but it is built as a pane so that becomes a toggle later. A photo is not pinned to a harness or endpoint; the caption carries "rear bulkhead, left side" until a drawing session against real photos shows a need to jump between them. The decision was made on the ticket [Where do reference photos live, and how does the board show them?](https://github.com/alexchunlin/harnessy/issues/39).

## Considered options

- Photos outside the project, referenced by absolute path. Rejected: the path breaks when the folder moves or opens on another machine, and the project is the thing Alex commits and reopens.
- A list per topology under `canvas/`. Rejected: the same photo would be added to every topology, and the project has few topologies.
- A grid of every photo, or a scrolling strip of full-size photos. Rejected: the pane is narrow, and only one large photo with thumbnails stays legible in it.
- Dimness per photo, stored in the project. Rejected: nobody would tune it per photo, and a viewing preference in the project makes git diffs that say nothing about the design.
- Converting HEIC on the server. Rejected: it pulls in a native dependency for a format a phone can export around.
- Pinning photos to harnesses or endpoints now. Deferred: it needs a selection model that spans two panes, and there is no evidence yet that it earns one.
